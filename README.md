# AI Git Flow CLI

Консольный Git-ассистент на языковых моделях. Раскладывает изменения по логичным коммитам в формате [Conventional Commits](https://www.conventionalcommits.org/), создаёт ветку, отправляет её на сервер и открывает pull request. Умеет также генерировать `README.md`, файл `LICENSE` и issue на GitHub.

Работает в Windows, macOS и Linux. Подключается к GigaChat и к любому OpenAI-совместимому API (DeepSeek, Grok, OpenRouter, Groq, OpenAI, локальный Ollama и другие).

```bash
npx ai-git-flow init     # один раз: выбрать провайдера, ввести ключ, проверить модель
aigf                     # дальше: ветка, коммиты, push и pull request одной командой
```

Пакет называется `ai-git-flow`. После установки доступны две одинаковые команды: короткая `aigf` и полная `ai-git-flow`. В примерах ниже используется `aigf`.

> Это кроссплатформенная версия на Node.js. Первая версия для Windows PowerShell лежит в репозитории [AI-Git-Flow](https://github.com/wildkodokushi/AI-Git-Flow). Команды версий различаются (`aiflow` у PowerShell-версии, `aigf` здесь), поэтому их можно держать на одном компьютере одновременно.

## Как это работает

Работа разделена между кодом и моделью. Это главное архитектурное решение: так утилита остаётся надёжной даже со слабыми моделями.

- **Код группирует файлы.** Тип каждого файла (зависимости, CI, конфигурация, ресурсы, исходный код, стили, тесты, документация) определяется правилами, исходный код делится по каталогам. Модель не решает, какие файлы объединять, поэтому результат воспроизводим.
- **Модель пишет только короткие тексты:** тему коммита для каждой готовой группы, заголовок и описание pull request, описание проекта для README, структуру issue.
- **Всё остальное проверяется кодом.** Ответ модели разбирается строгими парсерами. Тема приводится к повелительному наклонению (`added` превращается в `add`), тип коммита валидируется, а при сбое подставляется шаблонное сообщение. Текст лицензии никогда не пишет модель: он берётся из шаблона.

Последовательность `aigf`: анализ изменений, план коммитов, подтверждение, ветка, коммиты, `git push -u`, pull request через GitHub CLI.

## Быстрый старт

Нужны [Node.js](https://nodejs.org/) 20 или новее и [Git](https://git-scm.com/). Для pull request и issue ещё [GitHub CLI](https://cli.github.com/) (`gh auth login`), остальное работает без него.

**1. Запустить мастер настройки:**

```bash
npx ai-git-flow init
```

Мастер проверяет окружение, предлагает выбрать провайдера, скрыто принимает ключ, при необходимости скачивает сертификат (для GigaChat), проверяет подключение, подбирает модели и в конце прогоняет тестовые запросы (`aigf doctor`, около 3 000 токенов). Настройки сохраняются в папку пользователя.

**2. Установить команду (по желанию):**

```bash
npm install -g ai-git-flow
```

Без установки можно каждый раз запускать `npx ai-git-flow`. Для частой работы удобнее установленная команда `aigf`.

**3. Работать:**

```bash
cd путь/к/репозиторию
aigf --dry-run        # показать план коммитов, ничего не меняя
aigf                  # выполнить
```

## Ручная настройка

Мастер можно не использовать. Всё, что он делает, сводится к двум файлам и одной переменной.

**Папка настроек:**

| Система | Путь |
|---|---|
| Windows | `%APPDATA%\ai-git-flow` |
| macOS, Linux | `~/.config/ai-git-flow` (или `$XDG_CONFIG_HOME/ai-git-flow`) |

Папку можно переопределить переменной `AIGF_HOME`. Команда `aigf config path` покажет точный путь.

**1. `config.json`.** Пример для DeepSeek:

```json
{
  "provider": "deepseek",
  "providers": {
    "deepseek": {
      "models": { "small": "deepseek-chat", "large": "deepseek-chat" }
    }
  },
  "defaults": { "lang": "en" }
}
```

Пример для собственного сервера с OpenAI-совместимым API:

```json
{
  "provider": "mycloud",
  "providers": {
    "mycloud": {
      "type": "openai",
      "baseUrl": "https://api.example.com/v1",
      "needsKey": true,
      "keyEnv": "MYCLOUD_API_KEY",
      "models": { "small": "fast-model", "large": "smart-model" }
    }
  }
}
```

`small` используется для тем коммитов, `large` для pull request, README и issue. Можно указать одну и ту же модель.

**2. Ключ.** Любой из способов, приоритет сверху вниз:

1. переменная окружения провайдера (`DEEPSEEK_API_KEY`, `GIGACHAT_AUTH_KEY`, для своего провайдера `keyEnv` или `AIGF_<ИМЯ>_KEY`);
2. файл `credentials.json` в папке настроек: `{ "deepseek": "sk-..." }` (с правами только для владельца; создаётся командой `aigf provider key`).

**3. Для GigaChat: сертификат.** Серверы Сбера подписаны российским корневым сертификатом НУЦ Минцифры. Скачайте его (раздел «Сертификаты» на странице https://www.gosuslugi.ru/tls) и положите в папку `certs` внутри папки настроек либо укажите путь в переменной `NODE_EXTRA_CA_CERTS`. Подходят форматы PEM и DER (`.pem`, `.crt`, `.cer`).

**4. Проверка:**

```bash
aigf doctor --quick    # только подключение и авторизация
aigf doctor            # плюс проверка модели (около 3 000 токенов)
```

## Провайдеры и требования к модели

| Имя | Описание |
|---|---|
| `gigachat` | GigaChat Сбера. Бесплатный Freemium, доступен из России. Модели по умолчанию `GigaChat-2` и `GigaChat-2-Pro`. |
| `deepseek` | DeepSeek. Подставляется `deepseek-chat`. |
| `grok` | xAI Grok. Модель выбирается из списка, который отдаёт API. |
| `openrouter` | OpenRouter: много моделей одним ключом. |
| `groq` | Groq. |
| `openai` | OpenAI. |
| `ollama` | Локальный Ollama (`http://localhost:11434/v1`), ключ не нужен, код не покидает компьютер. |
| свой | Любой OpenAI-совместимый адрес (`aigf provider add имя --base-url ...`). |

Названия моделей у провайдеров меняются, поэтому мастер запрашивает у API актуальный список и предлагает выбрать.

**Какая модель подойдёт.** Список «разрешённых» моделей быстро устаревает, поэтому требования описаны через возможности и проверяются автоматически командой `aigf doctor`:

- модель надёжно выдаёт **одну строку**, когда её об этом просят, и соблюдает заданный формат (`TYPE:`, `TITLE:`, `DESCRIPTION:`);
- ей хватает контекста примерно на 8 тысяч токенов;
- она отвечает на запрошенном языке;
- это обычная (instruct/chat) модель. «Рассуждающие» варианты тратят лимит на скрытое мышление и для коротких ответов подходят хуже. Утилита сама увеличивает лимит, если ответ пришёл пустым, но надёжнее выбрать обычную модель.

Проверка делится на два уровня. **Малая модель** (`small`) проходит два теста: формат темы коммита и язык ответа. **Большая модель** (`large`) проходит три: описание pull request, данные для README и структура issue. Если уровень не пройден, `doctor` предупреждает и подсказывает выбрать модель сильнее. Мой ориентир (оценка, которую подтверждает или опровергает именно этот тест): для тем коммитов хватает моделей класса 7B и выше, для README, PR и issue нужны заметно более сильные.

## Команды

### aigf (commit)

Ветка, коммиты, push, pull request.

```bash
aigf                              # интерактивно
aigf -b feat/header -y            # без вопросов
aigf --draft --lang ru            # PR черновиком, тексты на русском
aigf --no-pr                      # без pull request
aigf --no-push                    # только локальные коммиты
aigf --base develop               # PR в ветку develop
```

**Остаться в текущей ветке.** На вопрос об имени ветки введите точку:

```text
Текущая ветка: feat/header
Имя новой ветки (например, feat/home-swiper). Напишите . чтобы остаться в текущей ветке: .
```

То же делают `aigf --stay` и `aigf --branch .`. Коммиты уйдут в текущую ветку и будут отправлены на сервер, pull request при этом не создаётся. В основной ветке (`main`) внимательно читайте план перед подтверждением.

Перед построением плана индекс сбрасывается (`git reset`, файлы остаются), чтобы собрать коммиты с нуля. Отправка выполняется без `--force`.

### aigf readme

Создаёт `README.md`. Код определяет технологии, команды запуска (из `scripts` в `package.json`), дерево проекта, адрес для `git clone` (учётные данные из URL удаляются) и раздел о лицензии. Модель пишет описание проекта и список возможностей только по тому, что видно в файлах. Существующий файл не перезаписывается без подтверждения или `--force`. Всегда проверяйте результат.

### aigf license

Создаёт `LICENSE` из шаблона: `mit`, `apache-2.0`, `bsd-3-clause`, `bsd-2-clause`, `isc`, `gpl-3.0`, `agpl-3.0`, `lgpl-3.0`, `mpl-2.0`, `unlicense`. MIT, BSD, ISC и Unlicense встроены и работают офлайн, остальные тексты загружаются с `api.github.com`.

```bash
aigf license                                  # выбор из списка
aigf license --type mit --author "Иван Петров" --year 2026
```

Выбор лицензии остаётся за вами. Описания в списке справочные и не являются юридической консультацией.

### aigf issue

Превращает короткую заметку в issue (bug, feature или task) и создаёт его через `gh`.

```bash
aigf issue "Кнопка входа не реагирует на нажатие на телефоне"
aigf issue "Добавить тёмную тему" --labels enhancement,ui --lang ru
```

Модель не должна придумывать детали: неизвестное помечается «To be clarified». Если указанных меток нет в репозитории, создание повторяется без них.

### Служебные команды

```bash
aigf init                      # мастер настройки
aigf doctor [--quick]          # диагностика и проверка модели
aigf provider list             # провайдеры; * отмечает активный
aigf provider use deepseek     # сменить активного провайдера
aigf provider add mycloud --base-url https://api.example.com/v1
aigf provider key [имя]        # сменить ключ
aigf provider models           # модели, которые отдаёт провайдер
aigf provider remove mycloud
aigf config show | path | set <ключ> <значение> | unset <ключ>
```

## Параметры

| Параметр | Описание |
|---|---|
| `-b`, `--branch <имя>` | Имя новой ветки. `.` оставляет текущую. |
| `--stay`, `--here` | Не создавать ветку, PR не создаётся. |
| `--dry-run`, `--dry` | Показать результат, ничего не менять. |
| `-y`, `--yes` | Не спрашивать подтверждение. |
| `--lang en\|ru` | Язык тем коммитов, PR, README и issue. По умолчанию `en`. |
| `--draft` | Создать PR черновиком. |
| `--no-pr`, `--no-push` | Не создавать PR, не отправлять ветку. |
| `--base <ветка>` | Базовая ветка PR. Определяется автоматически. |
| `--remote <имя>` | Удалённый репозиторий. По умолчанию `origin`. |
| `--provider <имя>` | Провайдер на один запуск. |
| `--model`, `--pr-model` | Модель для коротких текстов и для PR, README, issue. |
| `--max-code-groups <2-10>` | Максимум коммитов с исходным кодом (по умолчанию 5). |
| `--max-diff-chars <число>` | Сколько diff отправлять модели на группу (по умолчанию 6000). |
| `--type`, `--author`, `--year` | Для `license`. |
| `--labels a,b` | Для `issue`. |
| `--force` | Перезаписать `LICENSE`/`README.md` без вопроса. |
| `--insecure` | Отключить проверку TLS. Небезопасно, только для диагностики. |
| `--quick` | Для `doctor` и `init`: пропустить проверку модели. |
| `-h`, `--help`, `-v`, `--version` | Справка и версия. |

## Настройки по умолчанию

```bash
aigf config set lang ru
aigf config set draft true
aigf config set maxCodeGroups 4
aigf config show
```

Ключи: `lang`, `remote`, `author`, `draft`, `maxCodeGroups`, `maxDiffChars`. Параметры командной строки всегда приоритетнее.

## Правила группировки файлов

Коммиты идут в порядке таблицы: сначала зависимости и инфраструктура, затем код, в конце документация.

| Группа | Файлы | Префикс |
|---|---|---|
| Зависимости | `package.json`, lock-файлы, `requirements.txt`, `pyproject.toml`, `go.mod`, `*.csproj` | `build(deps)` |
| CI и контейнеры | `.github/`, `Dockerfile`, `docker-compose*` | `ci` |
| Конфигурация | `*.config.*`, `tsconfig*.json`, `.eslintrc*`, `.gitignore`, `.editorconfig` | `chore(config)` |
| Ресурсы | изображения, шрифты, аудио, видео, PDF | `chore(assets)` |
| Исходный код | остальное, по каталогам (`src/components`, `src/pages`) | `feat`, `fix`, `refactor`, `perf` (выбирает модель) |
| Стили | `*.css`, `*.scss`, `*.less` | `style` |
| Тесты | `*.test.*`, `*.spec.*`, `tests/` | `test` |
| Документация | `*.md`, `docs/`, `LICENSE` | `docs` |

Правила описаны в `src/grouping.js`.

## GigaChat

1. В личном кабинете разработчика Сбера создайте проект GigaChat API и откройте раздел «Данные для авторизации запросов к API». Нажмите «Получить новый ключ» и скопируйте **Authorization key**. Scope для физических лиц: `GIGACHAT_API_PERS` (используется по умолчанию).
2. Выполните `aigf init`: мастер сохранит ключ, скачает корневой сертификат и проверит подключение.

Утилита сама обменивает ключ на токен доступа (он живёт 30 минут) и обновляет его. Бесплатный Freemium даёт ограниченный пакет токенов на срок, а не ежедневный лимит; остаток и срок смотрите в кабинете. Для физических лиц доступен один поток запросов, утилита работает последовательно, поэтому это не мешает. Условия тарифа определяет Сбер и они могут измениться, поэтому полезно иметь запасного провайдера: `aigf provider use <имя>` переключает его одной командой.

## Решение проблем

| Симптом | Решение |
|---|---|
| `aigf: command not found` | Установите глобально (`npm install -g ai-git-flow`) или запускайте `npx ai-git-flow`. После установки откройте новый терминал. |
| Не удалось проверить TLS-сертификат | Для GigaChat выполните `aigf init`: он скачает сертификат Минцифры. Либо укажите файл в `NODE_EXTRA_CA_CERTS`. |
| Нет соединения с сервером | Проверьте интернет, VPN и антивирус. Утилита игнорирует системный прокси, поэтому устаревшие записи после VPN ей не мешают. Работа через прокси пока не поддерживается: если выход в сеть возможен только так, используйте локальный Ollama. |
| HTTP 401 | Неверный или просроченный ключ: `aigf provider key`. |
| HTTP 402 | Закончились токены или средства на балансе. |
| HTTP 429 | Лимит запросов. Утилита повторяет запрос сама, при повторении подождите минуту. |
| Модель вернула пустой ответ | Выбран «рассуждающий» вариант. Выберите обычную модель: `aigf provider models`, затем `aigf init`. |
| В коммитах странные сообщения | Запустите `aigf doctor`: он покажет, справляется ли модель. Попробуйте более сильную `--model`. |
| `gh` не найден или не авторизован | Установите GitHub CLI и выполните `gh auth login`. До этого текст PR и issue выводится на экран. |
| Коммит прерывается ошибкой хука | Сработал pre-commit хук проекта. Исправьте замечания и запустите снова. |
| Ошибка прав в Linux/macOS при `npm install -g` | Используйте менеджер версий Node (nvm, fnm) или `npx`. |

Подробный стек ошибки: `AIGF_DEBUG=1 aigf ...`.

## Приватность и безопасность

- **Код уходит во внешний сервис.** Для тем коммитов модель получает список файлов и усечённый diff (по умолчанию до 6000 символов на группу), для PR добавляется статистика изменений, для README дерево файлов и до трёх фрагментов по 60 строк (файлы `.env` не читаются), для issue только ваша заметка, последние темы коммитов и список файлов верхнего уровня. Содержимое lock-файлов в запросы не включается. Для закрытого кода используйте локальный Ollama.
- **Секреты в коде.** Если пароль или токен попал в изменения, он попадёт и в diff. Не коммитьте такие файлы, добавьте их в `.gitignore`.
- **Ключи** хранятся в `credentials.json` с правами только для владельца (в Windows действуют права профиля пользователя) либо в переменной окружения. Они отправляются только провайдеру, который вы выбрали.
- **TLS** проверяется всегда. `--insecure` отключает проверку на один запуск.
- **`--force` для push не используется нигде.**

## Разработка и релизы

```bash
git clone https://github.com/wildkodokushi/AI-Git-Flow-CLI.git
cd AI-Git-Flow-CLI
npm test        # без зависимостей, нужен только Node 20+
```

Тесты используют настоящий git, локальный «удалённый» репозиторий, поддельный сервер модели (включая обмен ключа GigaChat на токен), частный удостоверяющий центр для проверки TLS и поддельный `gh`. Реальные сервисы они не вызывают.

**Публикация в npm.** Пакет публикует GitHub Actions по тегу версии (`.github/workflows/release.yml`).

Один раз подготовьте:

1. Аккаунт на [npmjs.com](https://www.npmjs.com/) с включённой двухфакторной аутентификацией.
2. Гранулярный токен доступа (Access Tokens, Generate New Token, Granular Access Token) с правом Read and write для пакетов. Токены с правом записи живут не дольше 90 дней, срок придётся продлевать. Если npm потребует код 2FA при публикации из CI, включите для токена опцию обхода двухфакторной проверки.
3. Токен добавьте в репозиторий как секрет `NPM_TOKEN` (Settings, Secrets and variables, Actions).
4. Проверьте, что в `package.json` поле `repository.url` указывает на ваш репозиторий: оно нужно для подписи происхождения пакета (provenance).

Для каждой версии:

```bash
npm test
npm pack --dry-run          # посмотреть, какие файлы попадут в пакет
# поднимите version в package.json, закоммитьте
git tag v2.0.1
git push origin main --tags
```

Workflow проверит, что тег совпадает с версией, прогонит тесты, опубликует пакет в npm с provenance и создаст релиз на GitHub с архивом `.tgz` и файлом контрольных сумм `SHA256SUMS`. Вручную загружать `.tgz` никуда не нужно.

**Без токена (доверенная публикация).** После первой публикации в настройках пакета на npmjs.com можно добавить доверенного издателя (Trusted Publisher): ваш репозиторий и файл `release.yml`. Тогда публикация идёт через OIDC без долгоживущего токена, а секрет `NPM_TOKEN` можно удалить. По документации npm для этого нужен npm CLI 11.5.1 или новее, workflow его устанавливает. Актуальные требования смотрите на https://docs.npmjs.com/trusted-publishers.
